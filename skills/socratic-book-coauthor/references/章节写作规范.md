## 二、对话推进 vs 知识点讲解（核心排版规则）

全书正文分两种清晰区分的文本，**二者交替但绝不混淆**：

| 文本类型 | 作用 | 形式 | 谁发出 |
|----------|------|------|--------|
| **对话推进** | 逼造物主想、拆错误直觉、落锤命名 | 一问一答，短句 | 老谟 / 造物主 |
| **知识点讲解** | 给历史结论、工程实践结论、详细知识点 | 独立成块 | 编者注 / 概念块 |

### 结构示例（对话引出 → 知识点成块 → 对话收束）

```markdown
**老谟**："既然认了二进制，那咱们来真的。把十进制的 '5' 写到二进制里，你会。"

**造物主**："会，101。"

---
**📐 知识锚点：整数十进制 → 二进制**

【历史溯源】……（谁、哪年、为什么、弯路，独立成块）

【工程实践】……（现实工程里怎么用、为什么这么选，独立成块）

【概念深挖】二进制知识点详解……（重要部分加粗）
---

**老谟**："漂亮。那 '0.625' 这个小数，二进制怎么写？"
```

**要点**：
- 老谟的对话**只推进**：反问、拆穿、命名。不给大段灌输。
- 知识点（历史/工程/深挖）**一律独立成块**，放对话轮之间或轮末，用 `**📐 知识锚点**` 或 `【标签】` 开头。
- 读者能一眼分清「这里在推」（对话）与「这里是结论」（知识块）。


## 三、原理对话 vs 计算实操（计算板块·硬性分离）

教材强调"从零推导"，但这不等于把**计算操作**也塞进对话。核心铁律：**对话只讲"是什么/为什么"（原理），所有"怎么算"（公式、步骤、速查、代码、习题、踩坑）必须从对话剥离，放在对话结束后的独立计算板块。**

### 为什么必须分离
- 对话负责让读者**理解原理**（跟着造物主推导"为什么这样"），节奏要轻快、专注。
- 计算负责让读者**会算**（公式、步骤、速查表），是"能造"的工具箱。两者混在一起，对话会被公式拖垮，原理被淹没。

### 判断标准
- 对话里若出现"具体怎么算"，老谟只引导到计算板块（"具体怎么算后面有专门的计算板块，你翻过去看就行"），**绝不在对话里讲计算步骤/公式/习题/代码**。
- 所有计算内容（公式、计算步骤、速查表、代码、习题、踩坑记录）全部放在对话结束后的独立板块，用 `---` 分割线明确分隔。

### 计算板块的标准结构（按顺序出现）
```markdown
---（分割线）
### 📐 知识锚点·计算速查
用表格/步骤列清计算规则、公式、记忆口诀。**只讲"怎么算"，不讲"为什么"**（原理已在对话讲透）。
例：牛顿-莱布尼茨公式的适用场景、计算步骤、常用原函数速查表、记忆口诀。

### 🔧 工程实践·计算案例
配 1 个 AI/计算机相关的真实计算场景，附 Python 代码（numpy/scipy/sympy 等常用库），代码注释贴合教材风格。

### 💡 造物主手记·计算踩坑
写 1 个计算时的典型错误，呼应原理内容，保持造物主"踩坑后顿悟"人设。

### 📝 自测题·计算类
2-3 道计算题，难度易→中，附简答要点。用场景化表述（如"造物主要算匀加速位移"而非"求∫2t dt"）。
---（分割线，与后续原有内容分隔）
（后续原有内容：向导便签、知识点总结等完全保留）
```

### 绝对禁止
- ❌ 在对话里出现任何计算讲解、公式、代码、习题。
- ❌ 修改原有对话的任何内容（老谟和造物主的台词）。
- ❌ 把计算内容混进对话正文。
- ❌ 纯数学竞赛级复杂计算（难度控制在 AI/计算机入门够用）。

### 优先覆盖的 AI/计算机高频计算
- 微积分：求导法则、积分换元/分部、牛顿-莱布尼茨公式
- 线性代数：矩阵乘法、特征值/特征向量、逆矩阵、SVD 简化版
- 概率统计：正态/二项分布计算、期望/方差公式、极大似然、交叉熵
- 图论：Dijkstra 算法步骤、邻接矩阵↔邻接表

### 反例 vs 正例
```text
❌ 错误（把计算塞进对话）：
老谟："现在讲牛顿-莱布尼茨公式，计算定积分只要找原函数，公式是∫ₐᵇf(x)dx=F(b)−F(a)，你记一下。"
造物主："哦，那∫₀³2t dt 的原函数是 t²，代入就是 9−0=9 对吧？"

✅ 正确（对话只讲原理，计算单独放）：
老谟："你上次切 10000 条才算出来的 9，其实不用这么麻烦。积分是导数的逆，你只要找到那个'导数等于速度'的函数，就能直接得到总路程。"
造物主："哦！我之前算过 t² 的导数是 2t，那是不是 t² 就是我们要找的函数？"
造物主："那具体怎么找原函数啊？总不能每次都靠猜吧？"
老谟："具体怎么算后面有专门的计算板块，你翻过去看就行。我们接着讲原理。"
---
### 📐 知识锚点·计算速查：牛顿-莱布尼茨公式
【适用场景】求定积分，无需切条求和
【计算步骤】找原函数 F(x)（满足 F'(x)=f(x)）→ 代入 ∫ₐᵇf(x)dx = F(b)−F(a)
【常用原函数速查表】k→kx+C；xⁿ→xⁿ⁺¹/(n+1)+C；sin x→−cos x+C；eˣ→eˣ+C
【记忆口诀】找原函，代上下，后减前
### 🔧 工程实践·计算案例：（配 Python 代码）
### 💡 造物主手记·计算踩坑：（1 个典型错误）
### 📝 自测题·计算类：（2-3 道，含简答）
```

### 计算板块完成度检查
- [ ] 原有对话内容一字未改
- [ ] 对话里无任何计算步骤/公式/习题/代码
- [ ] 计算内容全部在对话结束后的独立板块，用 `---` 分隔
- [ ] 计算板块含：速查表 + 案例 + 踩坑 + 习题 四部分
- [ ] 代码符合教材 Python 风格（numpy/scipy 等库）
- [ ] 难度符合 AI 入门，无超纲


## 四、格式元素（知识点块标签）

### 1. 【概念深挖】
正文段落式详解，**关键知识点重要部分加粗**。可含公式、对照表、代码块。例子见 Ch1 小数转二进制、Ch2 卡诺图。

### 2. 【历史溯源】
给出**历史结论**：谁、哪年、为什么、走了什么弯路，独立成块，呼应「你不是第一个撞墙的」。例子见 Ch1 EDSAC/IBM System/360、Ch2 布尔 1854/香农 1937。

### 3. 【工程实践】
给出**工程实践结论**：现实工程里这个知识点怎么落地、工程师为什么这么选、有什么代价。与历史结论区分——这里讲"现在怎么用"，历史讲"当年怎么来的"。

### 4. 【图示】+ Mermaid
- 结构/流程/层级用 Mermaid `flowchart TD`。
- Mermaid 代码块**之后紧跟一段「读图说明」**，逐节点讲怎么读（这是全书特色，必须保留）。
- 需要精致插图时，另出 HTML+SVG 增强版。

### 5. 【实现思考】
**每章必须至少一处**，把「看懂」推向「能造」：
- 伪代码/Python 小片段 + 「为什么这么造」「代价」「换条路会怎样」三段式。
- 例子见 Ch1 补码 ALU 伪代码、Ch2 半加器 Python。

### 6. 【评价】
可选。对「是否值得学」给出清醒判断（如卡诺图值得学但不值得神化），防止读者把教科书当生产工具。

### 7. 对比块（可选）
```text
❌ 错误：……
✅ 正确：……
```
用于钉死常见误区（Ch1 原码 vs 补码、Ch3 子集 vs 元素）。


## 五、对话轮设计要点

1. **每轮有明确标题**（第 N 轮：轮次主题），主题是一小步推导。
2. **造物主先答，老谟后拆**：每轮必须由造物主先给出（错的/半对的）答案，老谟据此推进，不能老谟单方面讲。
3. **轮数 6-8 轮**：第 1 轮建立问题，最后 1 轮「落点」收束核心认知，中间轮次各推一小步。
4. **每轮信息量有节奏**：不追求每轮等长，「概念深挖/实现思考」所在的轮次更重。
5. **对话要有画面**：可穿插「我心头一紧」「他在桌上画了两条线」这类叙事线，防止变成纯问答稿。
6. **对话只推进不灌输**：老谟的对话负责反问、拆穿、命名；详细知识一律甩给独立知识点块，不在对话里长篇倒。
7. **对话不套路化（硬性）**：严禁每章重复同一套对白模板。具体要做到——
   - **换场景**：每章引子不都用"他敲了下桌子""我愣了一下"；可以是走路、画图、做饭、修东西、翻旧账等不同情境。
   - **换老谟的"把式"**：不要每轮都是"先戳破再点拨"。老谟有时直接甩一个反例，有时装傻，有时给个假答案让造物主去推翻，有时沉默等造物主自己慌。毒舌的 5 种类型（戳破/反讽/顺势/落锤/放大矛盾）要**轮换使用**，不固定用同一种。
   - **换造物主的"反应"**：不要每章都是"我心头一紧"。造物主可以有不服、有抢答、有死磕、有偷懒、有恼羞、有恍然大悟前的烦躁——情绪要有变化，不是每次被拆穿都是同一种表情。
   - **换推进路径**：不要每章都"造物主给错答案→老谟反问→造物主自己改对"。有的知识点适合老谟直接演示一个极端反例让造物主反思；有的适合让造物主自己动手算出一个荒谬结果；有的适合先给结论再回头补证明。
   - **换句式节奏**：老谟不要每次都"你总算会说人话了""又是约定"。同理的表扬/点评要换说法（"这就不赖了""勉强够格""你居然没翻车"）。
   - **一句话标准**：任何一章的对白，不该让你觉得"这在别的章节里也见过"。抽取两章同一角色的话，若有一半句式雷同，即判为套路化，需重写。


## 六、知识点总结小节（单章末尾必写）

位于对话引擎之后、向导便签之前。把本章推出的知识点集中收束，分三类清单，**重要知识点加粗**：

```markdown
## 知识点总结

### 知识点（本章推出的核心概念）
- **二进制**：机器选它是因为工程容错便宜，非数学必然。
- **补码**：把负数重编码进正数区间，让减法变加法。
- **编码**：比特本身无意义，意义来自约定。

### 历史结论（本章涉及的史料）
- EDSAC（1949）用符号位法，±0 并存；IBM System/360（1964）定补码为标准。

### 工程实践结论（本章知识在真实工程里怎么用）
- 浮点 0.1+0.2≠0.3：因 0.1 二进制无限循环，只能近似。
- ALU 因补码只需一个加法器，省下减法器电路。
```

**检查项**：
- [ ] 覆盖本章全部核心知识点，无遗漏
- [ ] 重要知识点已加粗
- [ ] 历史结论与工程实践结论分开列，不混
- [ ] 是「收束」不是「新增」：不引入对话里没推导过的新知识

## 八、每章必过清单（写作后自查）

- [ ] 对话轮数 ≥ 6
- [ ] 字数 ≥ 5000（成熟章 7000+）
- [ ] 从零推导：读者能跟着造物主推出结论，而非被告知；推论由最底层逐级构筑，逻辑严谨、清晰
- [ ] 实现思维深度：≥1 处「如果让你实现，你会怎么做」式追问
- [ ] 老谟人设一致（毒舌但不崩、不凶残）
- [ ] 概念约定被显式点明（「这是我们约定……」「约定就是规则」）
- [ ] 对话与知识区分清晰：老谟对话只推进，知识点独立成块
- [ ] 章末有「知识点总结」小节（知识点/历史结论/工程实践结论）
- [ ] 宁深勿浅：每个知识点都讲深讲透、让读者能「亲手造出来」；不限制知识点数量，但禁浅尝辄止（有"只讲名字不讲透"的知识点即不合格）
- [ ] 结尾有落地：本章推出的东西能干什么 / 下章预告
- [ ] 有自测题（含简答要点）与造物主手记


## 九、宁深勿浅的设计方法（章节规划时用）

宁深勿浅的核心是**讲得深**，不是限制知识点数量。判断标准：读者看完一章，对每个出现的知识点是"真懂了能造"，还是"听了个名字就走"——后者即浅。当一章出现以下情况时，考虑拆分或清单化处理（注意：拆分/清单化是为了保证每个点都讲透，而非因为"数量超限"）：

1. **按依赖拆分**：把「A 依赖 B」的知识拆成「B 章」+「A 章」，B 讲透再做 A。
2. **按难度拆分**：一个难概念单独立章，留足对话轮数让读者亲手推出。
3. **按深度取舍**：一章里并列的多个知识点，若确实无法都讲透，可把次要的降为"预告清单"（只列名+一句去向，不展开），把篇幅让给要深讲的核心点——但"降为清单"必须是取舍，不是偷懒，清单项也要说明将在哪章深讲。
4. 宁深勿浅的取舍：**多一章**好过**一章讲不透**。章节数目可自由增加，知识严谨性不可打折。宁可一章只讲透 2 个点，也不要一章囫囵讲 5 个。


## 十、语言与风格红线

- 中文写作，术语首次出现时给英文原名（two's complement、Boolean algebra）。
- 老谟毒舌自然，不硬凹不尴尬；禁止脏话和人身攻击。
- 「约定」意识贯穿：每个关键规则都要点明「这是我们约定的人为规则，不是天经地义」。
- 术语只在造物主推导到位后命名，禁止在推导前抛出。
- 确保知识推导符合逻辑与工程实践，同时不失去知识的严谨性：推导链不许跳步，工程结论要有现实依据。
