# 多 Agent 协作经验（来自《数学基础》一册实战沉淀）

> 本文件沉淀一次完整的多 agent 协作写书（《数学基础》4 幕 17 章 + 补强 + 全量重排）中积累的经验教训。供后续多章/多 agent 协作时复用。

## 一、协作分工模式

推荐的角色分工（一个团队一次写一部书）：

| 角色 | 数量 | 职责 |
|------|------|------|
| main（总协调） | 1 | 规划蓝图、分派章节、汇总统稿、全量重排、统一标准 |
| writer（章节作者） | 2-5 | 每个 writer 负责认知上连贯的 2-3 章（如数/逻辑、集合/函数、微积分） |
| reviewer（评审） | 1 | 按 skill 标准评审（内容+技术准确性+AI味+对话不套路化），提意见，复审 |

要点：
- **分批推进**：按幕分批次（如批1地基、批2变化），每批写→评→改→定稿后再启动下一批。避免一次性并行过多章导致标准失控。
- **writer 按认知依赖分组**：让一个 writer 写主题连贯的连续章（如多元微积分+最优化），保证内部风格一致、衔接自然。
- **reviewer 必须读 skill 标准**：评审前先读 SKILL.md + 章节写作规范 + 人物设定，建立风格基线。

## 二、对话不套路化的实战铁律（本次反复踩坑总结）

跨章雷同是最容易被忽视、但评审必抓的问题。以下是本次实际抓出的雷同类型与对策：

### 1. 引子反应词雷同
**踩坑**：多章引子都用"我一愣""我噎了一下""我愣住了"，跨章撞车。
**对策**：每章引子的角色反应词必须**全书唯一**。本次 17 章最终形成各不相同的一组反应词，如：我一愣/我眨了眨眼/我噎了一下/我手一顿/我梗了一下/直勾勾盯着/愣是没憋出/咬住下唇/眼皮一跳/心口一紧/低头看了看盒子/我眼睛一亮/手微微一缓/握旋钮的手顿在半空/嗓子发涩/抿了抿嘴/喉结一滚。
**评审动作**：reviewer 必须**跨章比对**引子反应词，而非只看单章。写作规范第 4 条「对话不套路化」的"一句话标准"要严格执行：抽两章同一角色的话，若一半句式雷同即判套路化。

### 2. 落点/收束句式雷同
**踩坑**：多章落点都用"绕了一大圈，回到你最初那个…"句式，批次内 3-4 章连续使用。
**对策**：落点收束也要换招——有的让造物主闭眼口述全章推导、有的回扣引子物品动作、有的用一个反例收尾。**若同一句式在多章出现，视为套路化，必须各自换招。**

### 3. 表扬句式雷同
**踩坑**："你亲手把…推出来了""你自己把这个…顺出来了""你把钥匙摸出来了"在多个 writer 间反复出现。
**对策**：老谟的表扬/点评也要轮换，避免"你亲手/你自己…出来了"这类庆祝范式。可用"这就不赖了""你自己掂量""这名字你没白起""把 sin 的底裤扒了个干净"等多样表达。

### 4. 强调句式重复
**踩坑**：某章"复杂函数，变成了加减乘除"出现 5 次以上。
**对策**：核心强调语全章控制 ≤2 次，其余换说法。

## 三、技术准确性评审要点（本次补强重点）

写作和评审都必须验证计算正确性，以下是本次抓出的数值错误：

### 1. 代码注释的期望输出必须实测
- 曾出现 Python 注释写的梯度期望值算错（0.9089 实为 0.7241），读者照跑对不上。
- **对策**：writer 写【实现思考】代码时必须亲手运行或手算核对注释里的期望输出；reviewer 要抽验关键数值（导数值、积分值、特征值、期望、熵）。

### 2. 概念表述的歧义要分清
- 期望 vs 样本均值：期望是分布的理论中心（总体属性），样本均值是估计值，"相等"只在长期平均意义下成立。不能混为一谈。
- MLE 的"更可能"：要说清是"更可能解释数据"（似然）而非"更可能为真"（后验，需先验）。
- 浮点比较：`==` 会翻车，要用 `abs(a-b)<eps`（容差）或 `np.isclose(a,b,rtol,atol)`（相对+绝对误差合成）。

### 3. 定理的条件要讲清
- Taylor 展开有收敛半径：ln(1+x) 只在 |x|<1 可信，sin/eˣ 全数轴收敛是特例。
- 幂级数不是对整个数轴都成立，必须点明"收敛半径"。
- 特征值正定 ⟺ 二次型恒>0（对称矩阵）。

## 四、宁深勿浅的正确执行

**宁深勿浅 = 讲得深，不是限制知识点数量。** 判断标准：读者看完一章，对每个出现的知识点是"真懂了能造"，还是"听了个名字就走"——后者即浅。

- 不因"知识点超过 N 个"就判超标。
- 每个知识点都要配推导或算例，讲透。
- 若某点确实无法当章讲透，才考虑拆章或降为"预告清单"（要说明去向，不是偷懒）。

## 五、全量重排的注意事项（本次踩坑总结）

当章节顺序因插入新章而重排时，必须同步处理：

1. **文件重命名**：用脚本两步法（先移临时名避免目标名冲突，再移最终名）。映射要精确。
2. **标题更新**：每个文件第一行 `# 第 NN 章` 的章号要同步改。
3. **正文章号引用**：正文里"第 X 章"交叉引用（如"承接第 9 章"）要按映射批量替换。**注意正文用一位数字（第 9 章）而标题用两位（第 09 章）**，正则要兼容 `\d{1,2}`。替换要跳过文件自己的标题行。
4. **预告衔接**：重排后每章末尾"预告"指向的下一章可能变了，要逐个检查并重写预告，让叙事链连贯。受影响的往往是插入点前后的章。
5. **清理套路句式**：重排是统一处理"绕了一大圈"等残留句式的好时机。

## 六、标准变更的同步

当用户澄清/修正某个标准（如"宁深勿浅"定义）时，必须：
1. 更新 SKILL.md 和所有 references 里的相关表述
2. **同步给所有协作 agent**（writer、reviewer），明确告知新口径
3. 让 reviewer 用新口径重新评估此前按旧口径的判定
4. 否则 agent 会继续按旧标准执行，造成返工

## 七、多 agent 协作常用话术

- 派任务时：给出文件路径、清晰的范围（只增不改/新增章）、硬性标准（轮数/字数/宁深勿浅/不套路化）、术语命名时机。
- 评审时：让 reviewer 给"逐维度评分 + 问题清单（引原文）+ AI味 + 结论（通过/需修改）"。
- 修订反馈：把 reviewer 意见原样转给 writer，标注必改/可选；改完发 reviewer 复审。
- 关闭：全书完成后向所有 agent 发 shutdown_request，全部确认后再 team_delete。
